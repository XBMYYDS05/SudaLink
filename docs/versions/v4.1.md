# 4.1.0 · 修 302 误判（“登录失败：网关返回 HTTP 302”）

## 现象

用户日志：

```
正在使用 移动 账号 23******26@zgyd 登录
账号 23******26@zgyd 登录失败：网关返回 HTTP 302
```

两个账号、每 10 秒一轮，一直失败 —— 但网络其实是通的。

## 定位

写了一个诊断探针，用真实账号打一次 POST，把原始响应打出来：

```
状态码  ：302 Found
Location：http://10.9.1.3/2.htm?wlanuserip=10.70.20.197&wlanacname=ME60-YYS1
          &wlanacip=221.178.234.23&mac=&session=&redirect=&ACLogOut=5
          &RetCode=2&ErrorMsg=Mg%3D%3D        ← base64("2")
正文长度：0
登录前能否上网：True
```

两件事同时成立：

1. **`RetCode=2` 是"本机已在线"**，302 是认证被受理后的正常跳转，不是错误。
   旧代码 `AllowAutoRedirect = false`，把任何非 2xx 一律当失败。
2. 既然已经在线，为什么还会去登录？因为**联网检测误判离线**。
   旧实现只探两个纯 HTTP 点（`msftconnecttest` / `firefox detectportal`），
   在校园网里很容易被劫持成 302，于是 `MatchesAsync` 要求 200 → 判离线 → 去登录 → 拿到 302 → 判失败 → 死循环。

两个 bug 互相咬住，缺一个都修不好。

## 修改

### 302 不再等于失败

`LoginAsync` 里先看正文；解析不出成功时，凡是"可能是成功"的状态码（2xx/3xx/空正文），
一律用**真正能不能上网**来判定：

- 3xx / 空正文 → 联网探测最多试 3 次（网关放行需要一点时间）
- 2xx 但有正文却解析不出结论 → 只试 1 次，避免密码错误时干等

判定逻辑抽成纯函数 `EvaluateLoginResponse(status, body, internetReachable, retCode)`，
这样它可以被单元测试覆盖，而不是只能靠真网关验证。

`RetCode` 会从跳转地址里读出来，用于更准的提示：

| 情况 | 提示 |
| --- | --- |
| 302 + 能上网 | 网关已跳转，网络已连通（成功） |
| 302 + 上不了网 + RetCode=2 | 网关说本机已在线，但实际仍然上不了网 |
| 302 + 上不了网 | 网关跳转（HTTP 302）后网络仍不可用，可能是运营商侧未放行 |
| ≥400 | 网关返回 HTTP 500（带具体码） |

### 联网检测改成多探测点并发

| 探测点 | 判定 |
| --- | --- |
| `http://www.msftconnecttest.com/connecttest.txt` | 200 且含指定文本 |
| `http://connect.rom.miui.com/generate_204` | 204 且正文为空 |
| `https://connect.rom.miui.com/generate_204` | 204 且正文为空 |
| `https://www.baidu.com/` | 200 且正文 > 512 字节（被劫持到门户页时长度对不上） |

**并发跑、谁先成功就返回**，整体耗时约等于最慢的那个而不是四个相加；
客户端超时从 5s 收到 3.5s，断网时不会让界面一直卡在"正在认证"。

### 顺手补掉的两个雷

- **GBK 解码**：网关结果页是 `charset=gb2312`，.NET 默认不带这个代码页，
  `ReadAsStringAsync` 会抛 `InvalidOperationException` —— 那个异常不在原来的 catch 列表里，
  会直接把后台守护循环带走。现在注册了 `CodePagesEncodingProvider`，
  并且 `ReadBodyAsync` 在字符集不支持时退回按字节解码。
- **APIPA 诊断**：本机地址是 `169.254.x.x` 时直接提示"没有拿到校园网 IP，请重连 WiFi"，
  比让用户盯着 HTTP 状态码猜要好。

## 验证

- 单元测试 7/7：新增「网关 302 跳转判定」5 个断言。
- 真网关探针：`Success=True  Message=网关已跳转，网络已连通`，登录前后联网检测均为 True。
- 应用实跑 26 秒（`--render --render-wait=26`）：概览页直接显示「网络已连接 / 网络连接正常」，
  日志只有启动两条，**没有任何一次多余的登录尝试**。

## 教训

> 判成功不要看"请求有没有报错"，要看**后果有没有发生**。
> 302 是 HTTP 的正常语义之一（"去看那边"），把它当归一化的失败，
> 等于假设了"网关只会用 200 回答我"。
